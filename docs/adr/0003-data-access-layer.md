# ADR-0003 — SQL-first migrations, Drizzle under a mandatory RLS wrapper, one audited service-role module

- Status: Accepted
- Date: 2026-10-11
- Audit refs: Q3 (option a), T3, E2, E3

## Context

- The spec lists "Drizzle ORM + Supabase SQL migrations", which gives two sources of truth for the schema. RLS policies, triggers and functions can only be expressed fully in SQL anyway.
- Drizzle connects to Postgres directly with database credentials. **It bypasses RLS** unless each transaction switches role and injects the JWT claims. The spec's "SQL via RLS" diagram is only true with such a wrapper.
- Order creation must be atomic: idempotency key, per-day number allocation, items, event. That needs real transactions. supabase-js (PostgREST) cannot do multi-statement transactions without moving logic into plpgsql.
- Anonymous customers have no Supabase user, so public writes need elevated privileges in a controlled place.

## Decision

1. **Single source of truth for the schema:** hand-written SQL migrations in `supabase/migrations/` (Supabase CLI). They include tables, enums, RLS policies, triggers, functions and grants. Never generated by drizzle-kit.
2. **Typed queries:** the Drizzle schema in `src/lib/db/schema/` is produced by `drizzle-kit pull` (introspection) after each migration and committed. CI fails if it drifts (`pnpm db:pull && git diff --exit-code`).
3. **Every user-scoped query goes through `withRls(claims, (tx) => …)`** (`src/lib/db/rls.ts`). It follows Drizzle's official Supabase RLS pattern:
   - open a transaction;
   - `select set_config('request.jwt.claims', $claims, true)` and `set_config('request.jwt.claim.sub', $sub, true)`;
   - `set local role authenticated` (or `anon`);
   - run the callback, and reset in `finally`.
4. **Lint rule:** ESLint `no-restricted-imports` bans importing the raw Drizzle client (`@/lib/db/client`) outside `src/lib/db/**` and `src/server/admin/**`. Feature code can only use `withRls` or the admin module.
5. **Service-role / privileged path:** a single module `src/server/admin/` (`import 'server-only'`) holds the only privileged DB client and the Supabase secret key. Each exported function:
   - validates its input with Zod;
   - checks its business preconditions explicitly (table token, client session, opening hours, plan flags, rate limit);
   - writes an `audit_logs` row when the action is sensitive.

   It is the path for public writes (orders, service requests, feedback), shadow-user session minting, cron callbacks and Super Admin actions. Changes to this folder get extra review (a `CODEOWNERS` entry once the repo has collaborators).

6. **Public menu reads** go through a `SECURITY DEFINER` SQL function `public.get_public_menu(slug text, locale text)`. It returns the full menu as JSON in one round trip, with an explicit column whitelist. It only returns visible, non-deleted rows of active or read-only-suspended restaurants.
7. **Connection:** `postgres` (postgres.js) through the Supavisor **transaction pooler** with `prepare: false`, as required by Supabase. Direct connection only for migrations.
8. **Tenant isolation is proven by tests:** pgTAP tests in `supabase/tests/` and Vitest integration tests through `withRls`. Every table gets: tenant A cannot read or write tenant B; each role sees only what the permission matrix allows; anon sees only the public surface. A CI check fails if a table has RLS disabled or has no test file referencing it.

## Consequences

- Business logic and transactions stay in TypeScript (`services/` stays pure and unit-testable). SQL holds integrity (constraints, triggers, RLS).
- Every request pays one extra round trip (the `set_config` calls), batched in the same transaction. Acceptable.
- Introspected Drizzle types lag a migration until `db:pull` runs. CI guards this.
